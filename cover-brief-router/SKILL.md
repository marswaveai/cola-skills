# 封面：例图选风格 → 确认文案素材 → 确认平台尺寸 → 确认后出图

用户选的是视觉效果，不是工具名。技能选择由你负责；不要把选技能的负担交给用户。此包负责交互、案例和依赖编排，不自带付费图像服务或第三方账号。

## 第零步：把随包依赖离线装好

在第一次处理制作请求时执行一次，纯解释/审阅流程不必触发。

1. 确定本包的绝对目录 `SKILL_ROOT`。用运行时已提供的技能根目录；若本包安装在技能目录下，同级目录就是默认安装位置。其他环境显式传 `--skills-dir`，不要写死开发者路径。
2. 有Python3与命令执行能力时，先跑安装模式（不是只跑 `--check`）：
   ```bash
   python3 "$SKILL_ROOT/scripts/ensure_dependencies.py" --json
   ```
   十个出图技能已随本包附带，脚本会先把它们离线解包到技能目录（默认 `~/.cola/skills`；本包在该目录内则装到同级），再返回每项状态。正常路径不联网：结果里 `network_downloads` 应为 0，`counts` 应全为 `installed` 或 `existing`。
3. 需要复核而不想落盘时，用只读检测：
   ```bash
   python3 "$SKILL_ROOT/scripts/ensure_dependencies.py" --check --json
   ```
   它只读随包副本与已装目录，不创建技能目录、不联网。
4. 阅读结果中实际落盘路径，再读取所选技能的SKILL.md及必要引用。不要等待名字自动进入菜单才开始读取；也不要绕过运行时明确禁用的技能。Punk 的风格资源在包内已与相对引用对齐；已有旧安装若有本地styles但旧引用失配，按检测结果使用真实资源路径，不修改旧文件。
5. 只在随包副本缺失时（本包被解包工具裁掉 `vendor/`，既无 `vendor/<技能目录>` 也无 `vendor/cola-skills-bundle.zip`）才允许联网兜底：脚本按清单记录的官方公开仓库与固定 commit 下载。兜底失败时保留成功项，说明哪一种风格暂不可执行，并继续可用方向；不能声称依赖已装好。无Python3时，如果环境有可信技能安装能力，按清单官方来源安装缺失项；两者都无则说明装配受限，不伪装已完成。
6. 已装技能不覆盖、不强制更新，不带入其他人的人脸、账号或配置；显式关闭的技能不重新启用或另名安装；已存在但资源不全的项只报告，不覆盖原文件。技能安装与出图能力分开：仅在选定路线后检查图像后端、照片引用能力或浏览器渲染；缺凭证/素材时说明所缺的一项。不擅自安装全局软件、注册、支付或修改环境账号。归藏的HTML模板需要可用浏览器渲染；只拿其视觉词汇生图不能称原生渲染跑通。

详细命令、目录适配、失败处理和运行依赖见 `references/dependency-installation.md`。

## 先辨别当前阶段

- 正在搭建风格库：先给每个准备提供选择的技能补至少一张有出处、看得见的代表性成品，再补视觉差异明显的方向；不穷举所有风格。缺案例是待补项，不能以“不硬凑”为由省略整个技能后声称覆盖完整。参见 `references/case-coverage.md`。
- 作者有合适的封面/海报成品时优先直接收集；只有总览、内页或素材板时，不能冒充独立封面。列明需补做的单张样例与素材，获得制作授权后补做；它们与用户当前内容无关。
- 正在给某段内容做封面：使用已存例图走下面的交互；不要为“选择风格”先生成用户内容的封面。
- 用户只要求检查、解释或修正流程：修正并说明，不把这句话当成出图授权。

## 第一轮：看例图选风格

1. 如已收到文章或视频，先读取可获取的内容以理解主题；读不到就说明，不能伪称看过视频。网页描述不等于完整视频逐帧内容。
2. 从 `references/style-samples.md` 或其他有来源记录的图库中，默认展示 6–8 个视觉差异明显的代表方向，并标出最推荐的 1–2 个。内置12张中01–09是作者例图、10–12是本次新制样张；这两类都可用来选风格，但分别标明来源。优先覆盖有案例的六家：GBro、Punk、归藏、宝玉、喜茶风、萌粒IP，再加1–2个差异明显的Punk方向；依据实际可执行状态标注受限项，不把Punk的六张当成六家。推荐不等于选项上限：用户想看更多时，继续展示尚未展示的已有案例，不反复要求在第一批里选。不要重复堆同一家技能的相近人物构图，不把清单内页当封面。
3. 展示现成例图，编号按本次展示顺序连续排列。每张只写“风格名｜来源技能”。例图自带别的题目、人物、文字都可以，它只是外观参考；不要求中性占位文案，更不因此重新生图。
4. 明确说：“这些只用于选风格，文字和人物不照搬。你的内容我更推荐第 X 种，因为……”。已有偏好优先采用，不默认塞进用户明确拒绝的风格。
5. 只问：“你选哪种？”需要时附作者风格页供查看更多，不把全部风格展开。

## 第二轮：建议并确认封面文字、素材

等用户选定风格再进入这一轮。

- 已给内容：沿用，不再让用户重交。提炼一条核心观点，给 2–3 个短标题候选，并说明推荐哪个；候选不是已确认标题。
- 未给内容：请用户发视频、文章或主题。
- 若用户已给封面标题：照用，不擅改。若要修改，只给建议让他选。
- 封面不默认带三条要点；优先主标题 + 必要时一句副标题 + 主视觉。
- 只补会影响制作的缺口：要不要本人/原视频人物、必带截图或产品图、不可改的品牌名/数字、必要禁项。
- 照片里多人时先确认主体；不自动把其中一人认作用户，不擅存成永久默认人脸。
- 不把素材中未经核实的新闻传闻当作封面事实，不擅自用夸大指责替代原观点。

可合并发问：“标题我建议 A / B / C，推荐 A。人物用原视频这位，还是不放人？”避免机械地追问一整套已知信息。

## 第三轮：确认发布平台与尺寸

确认真正要发布到哪里，以及该入口的画幅/像素尺寸，再给针对性排版建议。内容来自哪个平台，不等于要发布到哪个平台；“符合小红书风格”也只是视觉要求，不等于选定小红书作为发布平台。

- 平台尚未明确：问“小红书、视频号，还是两个都发？”；其他平台按实际需求列出。
- 尺寸尚未明确：合并问“有指定比例或像素尺寸吗？没有的话，我按发布入口推荐，你确认后制作。”不要要求用户自己懂尺寸。
- 已明确的项目沿用，只问缺口。小红书竖版可建议 3:4；视频号等入口需核对实际展示及裁切方式，不能用来源链接或风格默认比例替代确认。
- 平台和尺寸确定后，针对该入口建议标题大小、主视觉位置、安全区等，风格和已确认文字保持不变。
- 多平台时说明各需什么版本与张数，不默认同一张直接裁切就够。

## 第四轮：复述制作方案，等确认

平台和尺寸得到确认后，读取 `references/router.md`，按已选效果、素材与输出要求选技能；用户不需要再选技术路线。

确认内容包括：
- 风格及例图编号
- 主标题、副标题（如有）
- 人物或素材
- 发布平台、画幅与张数
- 使用哪个技能，出图后端是否可用

简短模板：
“用 X 技能做 Y 风格，主标题‘…’，人物/素材用…，出一张…规格的封面。可以开始吗？”

用户给了明确的制作确认才执行；挑风格、发素材或认可流程本身，不自动等于批准最后成品。

平台裁切规则不统一时说明核实范围，不把一条非官方尺寸说成唯一规范。下游技能有固定画幅时，不承诺它能直接输出冲突比例。

## 执行与验收

- 读取选定下游技能及必要风格模板，向它传入已经确认的需求，不重复三轮提问。使用 `references/confirmed-brief-template.md` 保存到当前任务目录的brief.md。下游的默认多张、重问平台或选风格不覆盖用户已确认的一张和既定选择；但首次必要配置、身份锚点及资源条件不能假装满足。按 `references/execution-adapters.md` 处理各家的接口差异。
- 需要实际图像生成时，先检查可用后端；技能编排提示词不等于拥有出图服务。
- 检查实际尺寸、完整文字、裁切与遮挡、人物和素材正确性。
- 有问题如实说明并针对性修正；可用图像编辑能力局部修正或重新生成，不通过代码覆盖或重写成图文字。重大换风格、换标题、换主体须再次确认。
- 按当前环境的可见文件/媒体交付方式交付成品，逐张显示，不只给文件路径。核对实际像素尺寸、完整文字、与选定例图的关键风格特征、裁切遮挡和素材身份。不把技能安装测试当成出图全链路测试；不能把作者示例、自己的试验图或内部审美评价冒充本次用户确认的成品。
